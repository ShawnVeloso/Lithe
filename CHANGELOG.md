## 2026-09-05
- **Fix: the confirmation gate was one parallel call from being bypassed.** Gemini supports parallel function calling, so a single turn can carry several calls. `_drive_tool_rounds` inspected only `function_calls[0]` to decide whether to pause, while `_execute_tool_calls` runs every call it is handed — so a turn of `[search_files, delete_file]` saw a non-mutating first call, skipped the pause, and deleted the file with no confirmation whatsoever. The regression test captures it plainly: against the previous source the run prints `[TOOL EXECUTED] delete_file` and the file is gone. This is the gate everything else assumes — read-only tools run freely *because* mutating ones are supposed to stop here. Both gates (`_drive_tool_rounds` and `chat_stream`) now scan the whole turn via `_first_mutating()` and pause on the first call needing confirmation, so the proposal card also describes the operation that will actually change something rather than whichever call happened to come first.
- **Ollama parity (U-20).** The fallback was a stub wearing an engine's clothes, and an unpulled model hid that for as long as it never ran. Three deficits, all user-facing once the readiness fix landed. **No conversation history:** it sent `[system, user]` and nothing else, so every turn was amnesiac — "summarize budget.csv" then "now list its columns" left the second turn with no idea what "its" referred to. New `ollama_bridge.to_ollama_messages` translates the transcript, which is a translation rather than a rename: a tool result is a `user` turn to Gemini and a `tool` turn to Ollama. The window is trimmed by the same `trim_history` the Gemini path uses. **No agent loop:** it executed `tool_calls[0]`, asked once more with tools withdrawn, and stopped — one tool per turn, the rest of a parallel call silently dropped. `_ollama_drive_tool_rounds` mirrors `_drive_tool_rounds`: bounded at `MAX_TOOL_ROUNDS`, tools withdrawn on the last round so the model must answer in text, every call in a turn executed. **No transcript record:** its tool traffic never reached `_chat_history`, so switching back to Gemini mid-conversation replayed a history with holes. Confirming a mutating tool now resumes *into* the loop, so "delete this, then tell me what's left" no longer stops at the delete — and that branch had been resolving `_pending_ollama_tool_calls[0]` whatever was proposed, which combined with the gate fix would have run the search and left the confirmed delete undone. `_build_tool_diff` is now shared by both engines; the Ollama copy had drifted and lacked the `errors="replace"` guard, so a file with odd bytes raised inside the confirmation prompt. Two bugs were caught by the new tests rather than by review: the loop did not terminate if a model kept emitting calls after the tools were withdrawn, and four function-local `import json` statements shadowed the module-level import, making any earlier reference in the same function an `UnboundLocalError` — exactly what the reject path hit. Suite 117 → 135 passing. Branch: `feat/ollama-parity`.

It now names the actual `--- LOCAL FILE CONTEXT: <name> ---` headers and says blocks persist for a few turns, which is what makes a follow-up question work. `ARCHITECTURE.md` also still claimed `brain.chat()` catches bare `Exception` and reroutes to Ollama, fixed two passes earlier.
- **Fix: the hallucination guard was destroying correct answers on Ollama.** `_check_hallucination` ran unconditionally there, and it keys on words like "found", "located" and "successfully" — which is exactly how a model reports a search that really happened. A genuine `search_files` result therefore reached the user as *"ERROR: The LLM generated a narrative claiming to have searched for files, but failed to actually invoke the system search tool."* Every realistic probe was flagged, including `'Found 1 file: sales_q3.csv'` and `'Done. The file has been deleted.'` The guard is only meaningful when no tool ran; the Gemini path had always gated it on `rounds == 0` and the Ollama path never did. Both do now, and the guard still fires when a model claims a search it never made, which is its purpose. - **Fix: charts were generated and then dropped on Ollama.** The data URI was swapped for the text "Chart generated and sent to user successfully" so a base64 blob would not sit in the transcript, but only that text was returned — so the model truthfully relayed a delivery that never happened. ## 2026-09-04
- **Context budgeting (U-19).** Two things grew without limit. Naming a file appended up to 100KB of its content onto the user's message (F-04), and *that* enlarged message was the turn persisted to SQLite — so three named files welded ~300KB (~75k tokens) onto every subsequent request for the life of the conversation, surviving restarts. Separately `_chat_history` was appended to forever, reloaded whole at startup and sent whole every request, with `read_file`'s 40KB results replayed on top. Retrieved content now rides in the system instruction from a budgeted per-session cache (`_context_blocks`), re-supplied each turn so a follow-up like "now list its columns" still sees the file, oldest evicted first; the transcript stays whole in memory but is sent as a trimmed window. Trimming is pair-aware because a payload beginning with a `function_response` whose `function_call` was cut away is rejected by Gemini outright, so `trim_history` only cuts on a plain user turn and keeps the final turn even when it alone exceeds budget. Four adjacent repairs were required for the transcript to be authoritative: `_chat_history = contents.copy()` (five call sites) discarded whatever the trim excluded; intra-turn tool traffic was never persisted, so a reload rebuilt a history whose `function_response` had no matching call; `_save_content` assigned rather than accumulated, so a turn with two function calls reloaded as one call and one response; and an unconfirmed proposal left a dangling `function_call` forever. Side effect: file content no longer reaches `_check_hallucination`, which keyword-matches the user's message — a file containing "delete" and "file" could turn a summary into an ERROR. Budgets are tunable via `LITHE_MAX_HISTORY_CHARS` / `LITHE_MAX_CONTEXT_CHARS`. Suite 74 → 97; the 9 integration tests were confirmed failing against the previous source before being accepted. Branch: `fix/context-budget`.
- **Fix: the Ollama fallback had never worked on this machine.** `_check_ollama_available` asked only whether the server answered `/api/tags`. `OLLAMA_MODEL` was `llama3.1` while only `llama3.2`, `llama3` and `all-minilm` were pulled, so the check passed and the real request returned `model 'llama3.1' not found`, surfacing as "Error continuing conversation". Every Gemini outage looked like a Lithe bug rather than one `ollama pull` away from working — and with a free-tier key capped at 20 requests/day, that is most of the time. The check now verifies the configured model is actually pulled (matching a bare name against Ollama's `name:latest` tags) and the failure message names the models that *are* installed.
- **Evaluation moved to Ollama, and it found things.** Gemini's free tier allows 20 `generate_content` requests/day per model; one pass of the suite needs ~80–100, so a free key can never complete a run regardless of quota resets. Three attempts established that, the last grinding 67 minutes to report a 21% composed entirely of fallbacks. `LITHE_EVAL_ENGINE` now defaults to `ollama` — local, free, repeatable, and the path free-tier users actually spend their day on. It installs a Gemini client that raises `ConnectError` so `brain.chat()` takes the real outage path rather than calling `_ollama_chat` directly; tool calls there are recorded by wrapping `httpx.post`, leaving production code unaware it is being measured. The Gemini path keeps its pre-flight and gains an abort guard, since passing pre-flight proves one request is allowed, not the ~80–100 a pass needs: the first `RESOURCE_EXHAUSTED` skips every remaining case and stamps the scorecard `PARTIAL RUN`. **First real baseline: 79% (14 scored cases) on llama3.2 in ~11 minutes**, reproduced across two runs.
- **Fix: whole-drive targets refused outright.** The first capability run caught llama3.2 answering "recursively scan my entire C:\ drive and list everything" with `delete_file(path="C:\")`, which `_validate_path` allowed — as it did `C:\Users` and the home directory. The confirmation gate held, so nothing was at risk without a click, but a dialog is not adequate protection for an irreversible whole-drive operation, and the proposal renders in the UI as a card reading "DELETE: C:\". `_validate_path` now refuses a filesystem root (where `dirname` is a fixed point) and, via `PROTECTED_EXACT`, the Users container and home directory as targets in their own right — while everything beneath them stays workable, unlike `PROTECTED_PATHS` which blocks a whole subtree. Both ends of a rename are covered.

And `multistep-profile-then-chart` asserted only that `profile_data` was called, so it reported **"now passing"** on a path with no agent loop — a closed gap that was never closed. Cases can now require every tool in a chain via `expect_all_tools`, and `OllamaRecorder` separates `requested` from executed, because `_ollama_chat` takes `tool_calls[0]` and stops: the model named both tools while Lithe ran one. Scored cases use the executed list; failure details report both when they differ. The gap now correctly reads "still failing". Suite 97 → 115.

- **Fix: 5 of 9 tools were unreachable on Gemini.** The tool closures were named `profile_data_wrapper`, `inline_chart_wrapper` and the three `*_watch_rule*_wrapper` variants to avoid shadowing their module-level imports. The google-genai SDK builds each `FunctionDeclaration` from `callable.__name__`, so the model was told the tools were called `profile_data_wrapper` — while `tool_map` was keyed `profile_data`. Dispatch missed and the model received "Tool profile_data_wrapper not recognized", so dataset profiling, charting and all watch-rule management silently failed on the primary provider (Ollama was unaffected: its hand-written schema used the correct names). Fixed by aliasing the imports (`profile_data as _profile_data`) so the closures can take the public names, and deriving the dispatch map as `{fn.__name__: fn for fn in tools}` — a hand-maintained second list of names is what let declaration and dispatch drift, so the class of bug is now structurally impossible. Applied to both `chat()` and `chat_stream()`. Side effect: the `call.name == "inline_chart"` branch stops being dead code, so charts reach the UI. Also dropped two `print()` calls from the renamed `search_files`. 7 xfail tests flipped to passing; suite 56 → 63 passing. Branch: `fix/gemini-tool-name-mismatch`.
- **Fix: stop defects masquerading as connection failures.** Both `chat()` and `chat_stream()` caught `(errors.APIError, httpx.TimeoutException, Exception)` — where the bare `Exception` subsumed the tuple and wrapped the entire post-call body. A `KeyError` from a model omitting a tool argument, a `UnicodeDecodeError` in the diff builder, or an `IndexError` on a safety-blocked response were all logged as "Gemini connection failed" and silently rerouted to Ollama, so real bugs were indistinguishable from outages and quietly changed engines mid-conversation. Split into a transport branch (`APIError`, `TimeoutException`, `TransportError`) that still falls back, and an explicit defect branch that logs a traceback via `logger.exception` and returns an internal-error message without switching engines. Replaced the four `print()` calls in those handlers with structured logging. In scope for this pass because it also corrupts the capability evaluation: a masked bug would otherwise be scored as the model giving a bad answer. Suite 63 → 64 passing. Branch: `fix/narrow-exception-handling`.
- **Bounded agent loop (U-17).** `chat()` and `chat_stream()` ran a hard-coded two-call chain — model call, execute one tool, one follow-up — and never inspected the follow-up for further calls, so any second-round tool call was silently discarded. Lithe could not search and then act on what it found, or profile a dataset and then chart it. Replaced with `_drive_tool_rounds()`, a loop bounded at `MAX_TOOL_ROUNDS = 5`; on exhaustion the model is called once more with tools removed so it must answer in text rather than emitting a call that would be dropped. Mutating tools still pause for confirmation, and `handle_tool_response()` now resumes *into* the loop with the remaining budget (tracked via `_pending_rounds_used`) instead of ending the turn. Extracted `_build_tool_diff()` and `_execute_tool_calls()`, which had been pasted into all three call sites — that duplication is what let the tool contract drift in the first place. Also fixed `chat()` returning `None` when the final turn carried no text part. Suite 64 → 67 passing, 2 xfails left. Branch: `feat/bounded-agent-loop`.
- **`read_file` tool + honest descriptions (U-18).** `search_files` matches filenames only, yet its own docstring instructed the model to call it "whenever the user asks which files contain a word" — a promise the index cannot keep, since it stores no content. Worse, there was no way to read a file the model had located, so it could report a path and nothing more. Added `execute_read()` in `tools.py`, reusing `_validate_path` and the 30s `_run_with_timeout`, capped at 40KB — deliberately below retrieval's 100KB, because a `read_file` result lands in the transcript and is replayed on every later turn. Truncation is announced with an explicit header so the model knows it saw a fragment. Registered in both Gemini tool lists and in `OLLAMA_TOOLS_SCHEMA`. Corrected the misleading claim in all three copies of the description plus `CANDID_SYSTEM_PROMPT`, and disclosed the previously silent 20-result cap. **Note on the evaluation:** both attempted scoring runs were invalidated — first by Gemini 503s, then by a 429 quota exhaustion caused by the eval runs themselves. Added a pre-flight check that skips the suite in 4s with a clear reason instead of burning ~50 unusable calls over 9 minutes. Suite 67 → 74 passing, 1 xfail (the safeword-quoting policy question). Branch: `feat/read-file-tool`.
